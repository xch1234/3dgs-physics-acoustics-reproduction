# 验证过程中的环境检查范围修正

初始通用检查对Windows physgaussian同时导入numpy和scipy，实际返回ModuleNotFoundError: scipy。读取原run_mpm.py及该环境导出文件可见，此Windows环境仅用于Warp基础实验，原入口不需要SciPy；不能因此推断Linux完整3DGS环境不可用。保留失败命令和日志，并另按实际依赖检查。需要SciPy的本次数值检查使用已有acoustics或Linux physgaussian Conda。

初始检查还尝试pat-tools/bin/python，返回FileNotFoundError。实际该Conda前缀仅安装GSL/Boost头文件和库，没有Python；它的原运行脚本明确用另一个physgaussian环境执行Python。这里改用真实C++编译、链接和执行验证pat-tools资源，不安装或更改环境。

首次启动独立PAT构建进程时WSL返回Wsl/Service/0x8007274c，构建尚未开始。重试启动后两个C++构建和三个数值入口均实际完成；不是把启动错误当作科学检查通过。原3DGS训练在此期间仍持续运行。

以上均是本轮验证的原始失败尝试，必须与适用范围内的后续检查一起报告。

## 本轮补充执行中的两次诊断

media_and_syntax.py 首次通过 PowerShell 直接启动 WSL 时，WSL 的 localhost 代理提示被 PowerShell 包装为 NativeCommandError；内部 11 个视频解码与 Bash 解析检查均已完成。为消除最外层退出状态歧义，使用 capture_validation.py / subprocess.run 重新捕获真实子进程状态，返回 0。保留原 media-and-syntax.log 与 logs/captured-media_and_syntax.log。

fresh_cpu_pipeline.py 首次执行完 FEM 数值计算后，被原脚本的 Git 干净检查中止。WSL Git 把 Windows CRLF 文件视为修改；逐一与 HEAD 比较 51 个跟踪文件，43 个仅换行差异，规范化后零实质差异。重试仅对该子进程设置 GIT_CONFIG_COUNT=1、GIT_CONFIG_KEY_0=core.autocrlf、GIT_CONFIG_VALUE_0=true，没有写入仓库或全局 Git 配置。使用 fresh_cpu_pipeline_retry 子目录保存重试产物；原失败日志和部分输出保留。此后 FEM、PAT 和 WAV 检查实际退出 0。

## 材料检查的 Windows 路径限制

本轮把 Warp 缓存隔离到 verification_20261101/cache/warp_windows 后，Windows Warp 0.10.1 原生编译器返回 Failed to open output file，路径包含中文“复现”；失败发生在材料核执行前。未修改原环境或原代码。随后在已有 Linux Conda 中运行同一 validate_materials 数值函数，省略 Windows 专用 include-path 钩子，改用已有 ASCII 源码别名并把缓存、结果重定向到验证目录。Linux 实际执行成功，结果位于 materials_linux，原 Windows 失败日志保留。
